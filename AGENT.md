# AGENT.md — контекст для ШІ

Цей файл не для людей, які користуються MoneyFlow. Він для того, хто
працює з кодом: асистент, співрозробник, ви в самих через пів року.

**[README.md](README.md)** — як поставити й налаштувати. Тут лише те,
що з README не видно: чому обрано саме такий варіант, що вже
перевірено, що ламалося по дорозі, і що робити, якщо зміниться вимога.

---

## Шари і залежності

```
ui/        ← знає про DOM, нічого іншого
  ↓
core/      ← знає про мережу та сховище, нічого про DOM
  ↓
domain/    ← знає тільки про себе: числа, дати, хеші, підсумки
```

Правило одне: залежності йдуть **вниз**, ніколи вгору і ніколи
вбік між шарами. `ui` не імпортує `core/apiClient.js`. `core` не
торкається `document`. `domain` не знає про жодного з них.

Чому: проєкт без тестів і без збірки. Єдине, що рятує складність
у такому разом — це те, що кожен модуль має одну причину існувати.
Порушення цього правила виглядає безпечно («усього один `import`»),
а через рік дає цикл, який неможливо розібрати.

`main.js` — диспетчер: він знає про все і більше ніхто. Він не має
жодної бізнес-логіки, тільки порядок дзвінків.

## Пароль не залишає браузера

**Рішення.** Браузер рахує `SHA-256(пароль)` і це називається
`passwordHash`. У системі «пароль» — це хеш, а не відкритий текст.
На сервер іде лише доказ:

```
proof = SHA-256(passwordHash + timestamp)
```

Сервер бере той самий хеш із рядка `Users`, рахує
`SHA-256(хеш + той самий timestamp)` і порівнює. Таймстемп — щоб
перехоплений запит не можна було відіграти повторно.

**Чому саме так.** Запит до `exec` іде через CORS, тому власний
заголовок `Authorization` не долітає. Решта способів або вимагає
сервера (якого немає за задумом), або просто не працює з `simple`
content-type. Доказ — єдине, що влаштовується в `text/plain` і
при цьому одноразове.

**Що зламано свідомо.** Немає bcrypt/scrypt/argon2 — у Apps Script
для них немає ні ключів, ні CPU. `SHA-256` тут — це не вибір, а те,
що доступно.

**Чому не шифрувати пароль перед відправкою.** Ідея «зашифрувати в
браузері» додає нуль безпеки: ключ лежить у тому ж публічному
JavaScript на GitHub Pages, тобто доступний кожному, хто відкрив
сторінку. Вийшло б дорожче й небезпечніше — з'явився б код, який
треба ще й правильно зламати.

**Де пароль усе ж є.** Кейлоггер перехопить його в момент набору —
до того, як той перетвориться на хеш. Це межа захисту, не баг.

## Чому немає солі

У колонці `Users` немає окремої солі: зберігається просто
`SHA-256(пароль)`. Свідомий вибір на користь простоти.

**Що реально захищає сіль.** Лише **офлайн-підбір за готовою
таблицею** — хтось украв таблицю й проганяє популярні паролі без
перерахунку.

**Чого вона не захищає.** Від того, хто просто має доступ до
таблиці: сіль лежить у тій самій таблиці, поруч із хешем. Тобто
для нашого реального противника (доступ до `Users`) сіль — це
одна колонка без жодної додаткової користі.

**Ціна відмови.** Офлайн-підбір для нас **легший**. Умова: пароль
має бути довгим і не словниковим, бо блокування робий перебір
повільним, але не неможливим (`123456` — близько 6 днів).

**Коли переглянути.** Якщо таблиця колись опиниться поза межами
родини. Повертається за кількома рядками: `hashPassword(password,
salt)`, колонка `Сіль`, і `parsePeriodsList`-подібна валідація при
читанні.

## Немає зворотної сумісності

**Рішення.** Старих схем не підтримуємо: ані в таблиці, ані в
запитах, ані в сховищі браузера. Змінивши формат — старий просто
відмирає. Проміжних версій, які переводять старі дані в нові, не
пишемо.

**Чому.** Код, який читає два формати одночасно, удвічі складніше
перевірити й удвічі частіше ламається. Користувач один, вигода
дорівнює нулю, а ціна — постійна складність у кожній зміни.

**Що замість сумісності.** Перевірка і гучна помилка. Кожен аркуш
має список обов'язкових колонок, і `readSheetAsRecords` перевіряє
його **до** читання:

```
В аркуші Transactions немає стовпців: Сума. Перейменуйте їх у шапці
як у bootstrapSheets — сервер не читає старі схеми.
```

Перевіряються одразу всі відсутні, а не перший — щоб не виправляти
по одному за три заходи. Те саме з пейлоадами: невідомий тип
операції, некоректна дата, відсутній `ID` — усі падають явно.

Ідея проста: щоб помилку було видно на екрані редактора за секунду,
а не через тиждень, коли хтось поскаржиться, що підсумки порожні.

**Коли сумісність справді знадобиться.** Окреме рішення, з
міграцією, планом і тестами на міграцію. Не «за потреби».

## Коди помилок: SESSION_EXPIRED проти UNAUTHORIZED

Це найважливіша поділка у проєкті, і її легко зруйнувати «на всяк
випадок зробимо все одним кодом».

| | `SESSION_EXPIRED` | `UNAUTHORIZED` |
|---|---|---|
| Що сталося | підпис валідний, минув `expiresAt` | токен підроблений, акаунт вимкнено, пароль змінено |
| Повторний вхід допоможе | **так** | **ні** |
| Що робити з чергою | **лишити** | **викинути** |
| Що показує UI | екран входу | екран входу |

На екрані обидва виглядають однаково — і це правильно: користувачу
не треба знати різницю. Різниця потрібна черзі.

```js
AUTH_FAILURE_CODES = [unauthorized, sessionExpired]  // однаково для UI
isSessionExpired(error)                              // по-різному для черги
```

**Правило:** `SESSION_EXPIRED` ставиться **лише** за умови
`payload.expiresAt < Date.now()`. Усе інше — `UNAUTHORIZED`. Якщо
розширити `SESSION_EXPIRED` на випадок «пароль змінили», черга
залишиться назавжди й не відправиться ніколи.

## Черга належить логіну, а не браузеру

Ключ черги — `moneyflow.pending-entries.<логін у нижньому регістрі>`.

**Чому не одна черга на пристрій.** Спільна черга означала б, що
записи, зроблені під «Мамою», можуть потрапити в таблицю від імені
«Тата». Сервер підставляє ім'я із токена, тому сам запис вийде
правильним — але людина, яка його зробила, ніколи б про це не
дізналася, а бюджет сім'ї отримає запис не туди.

**Вихід чергу не стирає.** Він стирає лише кеш знімка, щоб наступна
людина не бачила чужих витрат на стартовому екрані. Черга лишається
в `localStorage` і дійде, коли ця людина знову увійде.

## Поділ сховищ: sessionStorage проти localStorage

Правило, з якого все випливає:

> У `sessionStorage` живе те, що **шкода тримати довше**.
> У `localStorage` — те, що **шкода загубити**.

| | де | чому |
|---|---|---|
| сесія | `localStorage` | інакше довелося б входити при кожному відкритті |
| черга | `localStorage` | втрата черги = втрата записів, зроблених без мережі |
| кеш знімка | `sessionStorage` | закриття вкладки знищує копію на диску |

Черга не могла переїхати в `sessionStorage` — це прямо суперечило
б буттю черги.

**Кейс, що все це вирішив.** Користувач спитав, що станеться, якщо
вірус-логгер украв би дані. Виміряли: кеш у `localStorage` містив
**усю історію відкритим текстом** — один `getItem` і в зловмисника
весь бюджет за роки. При тому, що таблиця була закрита паролями.

Тому кеш переїхав у `sessionStorage`. Зручність при цьому не
втратилась: `sessionStorage` переживає перезавантаження сторінки,
тобто дані на екрані з'являються миттєво, як і раніше.

**Чого це НЕ рятує.** Коду, вшитого в саму сторінку — він бачить
змінну. Людини, яка дивиться на екран. Власника Google-акаунта.
Крадіжки токена. Воно прибирає рівно той вектор, де бар'єр
мінімальний: тридцять секунд із розблокованим пристроєм.

## Бюджет із лімітів замість доходів

**Рішення.** Доходів у системі немає взагалі: у формі, у таблиці
операцій, у категоріях. Замість доходу показується **Бюджет** —
сума лімітів категорій на цей місяць. Залишок = Бюджет − Витрати.

**Чому.** Три причини, у порядку важливості.

1. **Приватність.** Доходи — те, що найчастіше стає причиною
   неприємностей: хтось глянув на телефон, хтось побачив екран.
   Вистаряє прибрати цифри, які не мають з'являтися на екрані.
2. **Одне джерело правди.** Ліміти все одно треба задавати: без них
   картка «Ліміти по категоріях» порожня. Тобто ви вже вирішуєте,
   скільки плануєте витратити. Бюджет — це сума тих рішень.
3. **Менше коду.** Зникає таб у формі, п'ять категорій-доходів,
   `TRANSACTION_KIND`, `KIND_LABELS`, `normalizeTransactionKind`,
   гілка типу в списку операцій.

**Що змінилось у сенсі цифр.** Раніше `Залишок` = доходи − витрати,
тобто «скільки грошей лишилось». Тепер `Залишок` = бюджет − витрати,
тобто «наскільки ми в плані». Це різні величини, і це навмисно.

Нульовий або від'ємний залишок — не помилка, а сигнал. Власник
категорично відкинув вимогу «не показувати залишок, поки не задано
ліміти»: адміністратор і так побачить нуль і вирішить сам —
збільшити ліміти чи залишити як є.

### Де живуть ліміти й чому це окремий аркуш

`BudgetLimits`: `Місяць | Категорія | Ліміт, ₴`. Одна строка на пару.

Розглянутий і відхилений варіант — стовпець на місяць у
`Categories` (`Ліміт 2026-01`, `Ліміт 2026-02`, …).

| | стовпці в `Categories` | окремий аркуш |
|---|---|---|
| через 10 років | 120 колонок, горизонтальний скрол | 120 рядків, звичайна таблиця |
| що читає сервер | усі колонки щоразу | лише рядки потрібного місяця |
| `Categories` лишається | каталогом із хвостом | каталогом |
| копіювання на новий місяць | так само | так само |

Власник запропонував окремий аркуш сам — і правильно: операція
копіювання однакова в обох варіантах, аgrowth проблема лише в
стовпцях. `readSheetAsRecords` читає `1, 1, останній рядок,
остання колонка`, тож 120 порожніх колонок читались би щоразу.

**Зв'язок за іменем — і чому він падає голосно.** `BudgetLimits`
посилається на категорію за назвою, тож назва стала зовнішнім ключем.
Перейменування категорії в `Categories` зробить рядки сиротами, а
бюджет по тих категоріях **тихо зникне**. Тому `readCategoriesWithLimits`
падає з `RequestError`, якщо бачить ліміт на невідому категорію —
інакше залишок просто збільшиться на суму ліміту, і ніхто не зрозуміє
чому. Той самий принцип, що й з перейменованими колонками.

### Активність категорії та ліміт — різні речі

`Categories` має колонку `Активна` (`Так`/`Ні`, порожньо = так).
`BudgetLimits` — ліміт на конкретний місяць.

Це два незалежні прапорці, і їх плутати — типова помилка:

| | `Активна` | `Бюджет` |
|---|---|---|
| що означає | «нею користуються зараз» | «скільки на неї заплановано тоді» |
| залежить від місяця | ні | так |
| навіщо | ховає категорію з форми | рахує бюджет і смуги |
| категорія без ліміта | лишається у формі | не входить у бюджет |

Перша версія робила навпаки — «категорія з'являється, якщо для неї
є рядок у `BudgetLimits`». Це плутало дві речі й мало другу
побічну: набір категорій у формі змінювався з місяцем, тож при
перемиканні список мигав. Власник це помітив і розділив прапорці
так, як є зараз: форма стабільна, змінюється лише картка лімітів —
і це правильно, бо це й відповідь на інше питання.

**Немає категорій «про запас».** Категорію приховують через
`Активна = Ні`; ліміт не задають, якщо на неї не планують. Жодних
`FALLBACK_CATEGORIES`, жодної «категорії, яка завжди доступна».

Чому так: якщо активних категорій немає, форма порожніє, кнопка
«Зберегти» заблокована, а на місці категорій — пояснення, що
йти треба в таблицю. Це **помилка конфігурації, яку видно одразу**.
Фолбек приховував би її доти, доки хтось не спробує записати витрату
в категорію, якої в таблиці немає. Власник назвав це влучно:
«краще відразу побачимо проблему конфігурації».

**Тип операції знято з обох аркушів.** `Тип` у `Transactions`
більше нічого не розрізняє, а колонка з `Витрата` в кожному рядку
лише питає «навіщо». `appendTransaction` відкидає запит із полем
`kind` — інакше застарілий клієнт у руках зміг би записати дохід,
якого ми вже не хочемо бачити.

**Транзакція з неактивною категорією лишається в історії** — з
іконкою й кольором, а не з нейтральною крапкою. Категорію могли
прибрати з таблиці після того, як записи вже були внесені; зникнення
їх з екрана було б тим самим тихим зникненням, якого ми уникали
всюди. Нейтральна крапка (`•`) лишається лише для категорії, якої
в `Categories` немає взагалі.

**Рішення.** Клієнт надсилає `periods` — список місяців, які він уже
має. Сервер читає тільки їх і повертає поле `periods` зі списком
того, що реально прислало. Клієнт замінює ними свої, решту не
чіпає.

**Чому.** `addTransaction` і `deleteTransaction` повертають знімок
одразу — інакше довелося б робити другий запит і чекати ще ~3 секунди.
Тому без фільтра **кожен введений запис тягнув би всю історію**.
При 250 байтах на операцію й 150 операціях на місяць через 5 років
це 2.1 МБ на кожне натискання «Зберегти».

**Чому саме «запитані», а не «поточний».** Якщо сервер віддавав би
лише той місяць, який відкритий, то додавання запису в квітні з
відкритим березнем стерло б березень. `periods` робить операцію
злиттям замість заміни.

**Два правила, які легко зламати:**

1. **`loadPeriod` бере місяць і попередній.** Попередній потрібен для
   «динаміки до попереднього місяця». Без нього показник був би нульовим.
2. **Несинхронізовані записи переживають злиття.** У знімку їх ще
   немає, тож наївний фільтр «замінити місяці, які прийшли» стер би
   запис, який користувач щойно ввів. Фільтр лишає `pending === true`.

Правило 1 уже дало один збій у власника: перший запит повертався з
одним місяцем, і «динаміка до минулого» не з'являлася. Тому
`withPreviousPeriod(periodKey)` живе в одному місці, а
`#requestedPeriods()` **завжди** додає відкритий місяць і попередній
до всього, що вже в пам'яті. Звідси й побічний ефект: одного виклику
`synchronize()` вистачає навіть для першого входу на місяць без даних.

### Ліміти не змішуються, бо їдуть окремо від операцій

**Проблема.** Запит іде щонайменше на два місяці. Сервер збирав
ліміти **всіх** запитаних місяців в одну мапу «категорія → сума», а
клієнт тримає **один** масив категорій. Жовтневий ліміт через це
показувався і в вересні, де його ніхто не задавав.

**Рішення.** У запиті два незалежні поля:

- `periods` — операції за цими місяцями;
- `limitPeriod` — **рівно один** місяць, чиї ліміти цікавлять.

`limitPeriod` завжди дорівнює відкритому місяцю.

**Чому не зробити категорії по місяцях на клієнті.** Можна було б
тримати `categoriesByPeriod`. Але картка бюджету показує тільки
відкритий місяць, тож один масив із правильною заміною вирішує те саме
десятьма рядками замість сотні.

**Наслідок, який легко пропустити.** Ліміти тепер «належать»
відкритому місяцю, а не тому, що останній прийшов у відповіді. Тому
`loadPeriod` не може короткозамикатися на «місяць уже завантажений»:
повернувшись на жовтень, треба показати жовтневий бюджет, а не той,
що був на екрані мить тому. Ліміти тримаються в
`#categoriesByLimitPeriod` — у пам'яті, не в кеші сторінки, тож
повторне перемикання миттєве й без запиту.

### Помилка про «порожній» місяць

**Симптом.** Вхід на місяць, у якому немає ані даних, ані бюджету,
залишає «Завантаження місяця…» назавжди.

**Причина — порядок викликів, а не дані.** `unlockApplication()`
виконує `synchronize()` **до** `revealApplication()`, а
`loadPeriod()` викликався лише з `requestSync()`, який при ручному
вході не запускається. `setActivePeriod()` виконувався теж пізно —
вже після першої синхронізації, тож запит будувався не для того
місяця, який мав лишитися на екрані.

Виправлено двома рядками: `setActivePeriod()` тепер виконується на
початку життєвого циклу, а `#requestedPeriods()` сам добирає
відкритий місяць.

**Загальне правило:** якщо запит будується за чимось, що задає
зовнішня сторінка, це «щось» має бути передано **до** першого запиту,
а не після нього.

**Межа 12 місяців** — запобіжник, а не план. Зазвичай у пам'яті
один-два місяці. Без межі список місяців перевищив би ліміт сервера
(`MAX_PERIODS_PER_REQUEST`), і тоді перестав би працювати сам
додаток: будь-який запис падав би з `BAD_REQUEST`.

**Чому відкритий місяць не можна викидати.** Двічі вже через це
залипали панелі на «Завантаження місяця…» назавжди:

- без `trimToLimit` — список місяців розрісся до 17 і ламав сервер;
- з простою межею — запит приносив потрібний місяць і тут же
  викидав його за межу пам'яті.

Тому `main.js` викликає `budgetStore.setActivePeriod()`, а
`trimToLimit(periodKeys, mustKeep, limit)` втримує відкритий місяць і
щойно прийшли.

**Чому читати двома проходами.** Спершу одна колонка `Дата`
(`findRowRangeByPeriods`), щоб знайти межі потрібних місяців, потім
смуга рядків із запасом на записи, додані заднім числом. На семирічній
історії — приблизно в п'ять разів менше клітинок за повне читання.

Фінальна фільтрація все одно точна, тож запас `PERIOD_ROW_WINDOW_PADDING`
впливає лише на повноту, а не на коректність.

**Фонове догруження сусідніх місяців відхилене свідомо.** Воно
платило б за кожен введений запис (а це 90% дій) заради рідкого
перегляду старого місяця. Власник сформулював це так: «найчастіша
операція — ввод видатків, іноді повернутися на місяць-два глянути».
Оптимізуємо під 90%, а не під 100%.

---

## «Завантаження місяця…», а не нулі

Поки місяць не прийшов, панелі ховаються і показується
`#periodLoading`. Наївний варіант — відрендерити порожні панелі —
виглядав би як «у цьому місяці ніхто нічого не витратив». Це не
відмінність у оформленні, це брехня в цифрах.

Форма вводу при цьому рендериться **завжди**: введення видатків не
має чекати на панелі.

## Порядок деплою

Зміни клієнта й сервера треба деплоїти в різному порядку залежно
від того, що саме змінюєш. Порядок не довільний.

**У агентів.** Дивись, що зробиться з **старою** версією іншої
сторони:

| зміна | старий клієнт + новий сервер | новий клієнт + старий сервер |
|---|---|---|
| фільтр місяців (`periods`) | старий не знає про звужений знімок → показує тільки поточний місяць, динаміка нульова | сервер ігнорує `periods` → працює як раніше |
| `SESSION_EXPIRED` | старий не знає коду → вважає це звичайною відмовою і **викидає чергу** | новий клієнт просто не отримає цього коду від старого сервера |
| відмова доходу | старий клієнт надсилає `kind` → отримає помилку, запист зупиниться в черзі | старий сервер прийме будь-який `kind` — але й не покаже |
| **нова схема таблиці** | — | — |

**Правило.** Якщо стара сторона **деградує** (показує неповні дані)
— деплой **сервер → клієнт**. Якщо стара сторона **ламається**
(втрачає дані) — деплой **клієнт → сервер**.

Конкретно:

- фільтр місяців → **Code.gs, нова версія, потім `git push`**
- `SESSION_EXPIRED` → **`git push`, потім auth.gs**
- відмова доходу → **Code.gs, нова версія, потім `git push`**:
  старий клієнт зупиниться на помилці запиту, але черга збережеться,
  бо це `BAD_REQUEST`, а не відмова в авторизації

**Повна зміна схеми таблиці — це не деплой, а переїзд.** Спочатку
готується нова таблиця, потім переноситься стара. Сервер до цього
моменту падає на `requireSheetColumns`, а не читає половину
таблиці.

**Apps Script завжди вимагає нової версії розгортання** після
зміни `.gs`. Просте «Зберегти» не працює.

## Як тестувати без Node

**Проблема.** Node у проєкті немає й не потрібен. А `.gs` треба
перевіряти перед тим, як віддати власнику на деплой.

**Компіляція `.gs`.** Відкрити сторінку локального сервера й у
консолі:

```js
const text = await (await fetch('/apps-script/Code.gs')).text();
new Function(text);   // кине SyntaxError, якщо код битий
```

Зробити це для **обох** файлів перед будь-яким прогоном.

**Пісочниця сервера.** Apps Script API не існує в браузері, тому
підміняємо його вручну. Ключовий момент — `with (sandbox)`, а не
параметри функції: параметри ламаються, коли ім'я з пісочниці
збігається з іменем із вихідного коду (`RequestError`, наприклад).

```js
const G = new Function('sandbox',
  'with (sandbox) {' + source + '\nreturn { readCategoriesWithLimits }; }'
)(sandbox);
```

Мінімально потрібні: `SpreadsheetApp`, `Utilities`, `Logger`,
`console`. `Sheet` — це об'єкт із `getLastRow`, `getLastColumn`,
`getRange(...).getValues()`, який повертає масив масивів.

**Дві пастки, на які я вже наступив.**

1. **Макет має читати таблицю живо, а не копіювати її.**
   `const all = [s.header, ...s.rows]` робить знімок на момент
   створення — і тест «додати рядок, перевірити помилку» не спрацює
   ніколи, мовчки.
2. **`new Function('')` не кидає помилки.** Якщо локальний сервер
   впав, `fetch` поверне порожній рядок, а «компіляція» пройде.
   Обов'язково перевіряти `text.length`, інакше результат тесту
   нічого не означає.

**Локальний сервер.** Часто порт 5500 зайнятий застарілим
powershell — гасити й піднімати знову. Після перезавантаження
сторінки мок `window.fetch` зникає, його треба ставити наново.

**Якщо `browser.evaluate` повертає `{}` замість значення** — це
не помилка коду, а те, що скрипт упав або завис. Перевіряти
консоль і пробувати `function () {}` замість `async () => {}`.

**Макет клієнта.** Підмінити `window.fetch` — тоді можна задати
серверну відповідь будь-якої форми й дивитися на реальний UI:

```js
window.fetch = async (url, options) => {
  const body = JSON.parse(options.body);
  return new Response(JSON.stringify(підготованаВідповідь(body)), {
    status: 200, headers: { 'Content-Type': 'application/json' },
  });
};
```

Перевірити пароль треба так само: `sha256Hex(sha256Hex(пароль) + timestamp)`
проти надісланого `proof`.

**Локальний сервер.** Часто порт 5500 зайнятий застарілим
powershell — гасити й піднімати знову. Після перезавантаження
сторінки мок `window.fetch` зникає, його треба ставити наново.

**`local-pass.txt`** у корені — чернетка пароля для локальних тестів,
у git не потрапляє (є в `.gitignore`).

## Виміряні числа

Тримати в розумі, щоб помічати регресії за цифрами, а не на око.

| що | значення |
|---|---|
| байт на одну операцію | ~247 |
| операцій на місяць у сім'ї | ~150 |
| повний знімок за місяць | 36 КБ |
| повний знімок за рік | 434 КБ |
| повний знімок за 5 років | 2.1 МБ |
| знімок одного місяця зараз | 26–36 КБ |
| клітинок прочитано на одному місяці | 12 188 з 84 008 (**−85%**) |
| запитів на `addTransaction` | 7 (було 38) |
| запитів на `deleteTransaction` | 7 (було 29) |
| запитів на `loadSnapshot` | 5 (було 19) |
| спроб на добу без блокування | ~144 000 |
| спроб на добу із блокуванням | 480 |

**Сценарії, які треба перевіряти після зміни будь-чого в
авторизації або черзі:**

1. перебір логінів не дає різниці у відповіді (немає витоку імен);
2. черга переживає вихід → перезавантаження → повторний вхід;
3. `SESSION_EXPIRED` не стирає чергу, `UNAUTHORIZED` стирає;
4. запис «заднім числом» у невідкритий місяць не зникає при перемиканні;
5. подвійний клік по «назад» дає один запит, а не два;
6. 60 швидких кліків «назад» не лишають панелі на заглушці;
7. кеш переживає перезавантаження сторінки й не потрапляє в `localStorage`.

**Після зміни моделі бюджету:**

8. `Залишок` = сума лімітів місяця − сума витрат;
9. у формі лише категорії з `Активна` ≠ `Ні`, у незалежності від ліміта;
10. категорія з `Активна = Ні` лишається в історії зі своєю іконкою;
11. ліміт на невідому категорію дає `SERVER_ERROR` на екрані редактора;
12. без активних категорій форма порожніє, кнопка заблокована;
13. `addTransaction` із полем `kind` відкидається;
14. вхід на місяць без даних не лишає «Завантаження місяця…»;
15. ліміти жовтня не з'являються в вересні, де їх не задавали.

## Відомі обмеження

**Не перевірено.** Відповідальність Apps Script за ліміти часу
виконання та розміру відповіді не вимірювалася. Не вимірювані
фактичні затримки на їхній інфраструктурі (2–3 с — це спостереження,
а не заміряна величина). Не перевірено поведінку на реальному
мобільному пристрої: усі перевірки йшли у Desktop Chrome.

**Побічні ефекти, які прийнято.**

- Поки місяць не прийшов, панелі порожні (заглушка). Це помітно
  на слабкому інтернеті.
- Офлайн-відкриття починається з порожнього бюджету, якщо вкладку
  закрили: кеш жив у `sessionStorage`.
- Зміна `tokenSecret` одразу вибиває всіх — зручно, але небезпечно,
  якщо зроблено випадково.
- Лічильник невдалих спроб спільний на всіх. Сім'я може заблокувати
  собі вхід, неправильно набираючи пароль п'ять разів поспіль.

**Правило для майбутніх змін.** Нову сутність не додавати в
`budgetStore` без питання «хто її власник». Стан належить або логіну,
або браузеру, або диспетчеру — і це видно з того, у якому сховищі
вона лежить. Якщо не зрозуміло, кому — значить, ще не вирішено.
